# RFC P0-1-09 — wire `@octc/findings` into the workspace lockfile

**Lane:** findings · **TODO:** P0-1-09 · **Raised:** 2026-09-09
**Owner of the fix:** Steward (`pnpm-lock.yaml` / workspace install)

Filed per the shared preamble and lane brief: this lane owns only
`packages/findings` and must not edit `pnpm-lock.yaml` or the root
`package.json`.

---

## Request

`packages/findings` (`@octc/findings`) is new under the existing
`packages/*` workspace glob. It follows the valuation/lots convention:
source-relative imports to sibling packages, no new external dependencies,
and a local `package.json` with `typecheck` / `test` scripts.

Please run a workspace install so the package is recorded in
`pnpm-lock.yaml` (same pattern as “Record the lots package in the lockfile”).
No root `package.json` script changes are required for P0-1-09.

## Impact if not fixed

Consumers that resolve packages only via the lockfile will not see
`@octc/findings` until Steward lands the install commit. Local vitest from
the repo root already picks up `packages/*/test/**/*.test.ts` without a
lockfile entry.

---

## Resolution (Steward, 2026-09-09)

Applied on `main`: `packages/findings` is recorded in the lockfile importers,
alongside the other dependency-free workspace packages.

One correction to the impact assessment, for future reference: a new package
with **no** external dependencies does not actually break
`pnpm install --frozen-lockfile` — it was verified passing on this branch before
the entry was added, so CI was never blocked. The entry is still worth landing,
because a plain `pnpm install` would otherwise leave an uncommitted lockfile diff
in every contributor's tree.

The distinction that does matter: a package declaring workspace **dependencies**
(as `rules-engine` and `source-registry` did in P0-1-04) *does* fail
`--frozen-lockfile` until the lockfile records them. Filing the RFC rather than
editing the lockfile was the right call either way.
