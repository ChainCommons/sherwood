# RFC P0-3-04 — a jurisdiction cannot depend on another jurisdiction

**Lane:** france · **TODO:** P0-3-04 · **Raised:** 2026-09-09
**Owners of the fix:** Engines (`packages/rules-engine`,
`packages/source-registry`), Steward (`schemas/`)

Filed per the shared preamble: everything below is outside
`jurisdictions/france` and `jurisdictions/eu`, so this lane did not touch it.
P0-3-04 ships green — `pnpm validate`, `pnpm typecheck` and `pnpm test` all
pass — and the EU pack's 25 rule tests were executed against `evaluate()` while
authoring. But the pack it delivers is a **dependency** pack, and the engine
has no concept of one.

Plan 15 §79 is explicit: *national packs SHOULD reference shared EU rules
rather than duplicate them*, and *France VAT rules `references: [eu:vat:...]`
rather than copy-paste*. Neither half of that is representable today.

---

## 1. A rule that cites another pack's source resolves to nothing, silently

`loadPack()` builds its `SourceRegistry` from `<root>/sources` only, and
`resolveAsOf()` drops any id it cannot find:

```ts
// packages/source-registry/src/registry.ts
for (const id of sourceIds) {
  const s = this.byId.get(id)
  if (s) out.push(viewAsOf(s, d))   // else: gone, no error
}
```

France already cites EU sources, as plan 15 asks. The result today:

```
fr-nft-vat-look-through-to-underlying-2024 cites 2 sources, resolved 1
missing: [ 'eu-dir-2006-112-vat' ]
```

Reproduce (with the YAML fix from RFC P0-3-03 §1 applied, or by parsing with
the `yaml` library):

```ts
const pack = loadPack('jurisdictions/france')
const r = evaluate({
  event: { event_type: 'NFT_SALE', asset_category: 'non_fungible_token' },
  participant: { capacity: 'MARKETPLACE_OPERATOR' },
  asOf: { transactionDate: '2024-06-01', analysisDate: '2026-09-09' },
  pack
})
r.applicable[0].sources.length   // 1, not 2
```

This is worse than a missing citation. `attachSources()` throws only when
`rule.sources` is empty, so **AC-001 is satisfied by an accident**: the rule
happens to cite one French source as well. A rule whose sources are *all*
foreign would come back with an empty `sources` array and no error at all,
which is the exact appearance of authority this project exists not to produce.
The count of contemporaneous sources — which AC-002 and the Time Machine read —
is understated for every France VAT rule today.

This was flagged as an aside in RFC P0-3-03 and is now load-bearing.

**Suggested fix**, smallest first:

- `LoadPackOptions` gains `dependencies?: readonly string[]` (pack roots).
  `loadPack` merges their `sources/` into the registry. A dependency's sources
  are readable; its rules are not loaded by this option.
- `attachSources()` fails loudly on an unresolved id rather than dropping it:
  `throw new Error(\`rule ${rule_id} cites unresolved source ${id}\`)`. A pack
  that cannot resolve its own citations should not evaluate.
- `packages/validate/src/checks/references.ts` already resolves cross-pack ids
  correctly, because it reads the whole `jurisdictions/` tree. That is why
  `pnpm validate` is green while the engine is wrong, and it is the same
  divergence RFC P0-3-03 §1 describes: two loaders, one truth.

## 2. `evaluate()` cannot run a dependency pack's rules

```ts
// packages/rules-engine/src/evaluate.ts
const candidates = pack.rules.filter(
  (r) => r.jurisdiction_id === pack.jurisdiction_id && ...
```

An EU rule can therefore never fire in a France evaluation, whatever the data
says. `jurisdictions/eu/rules/` now holds seven rules — the taxable-person
scope gate, arts. 44, 45 and 58, *Hedqvist*, the NFT absence marker, DAC8 — and
France cannot reach any of them.

The workaround this lane refused to take is the one plan 15 §79 names: copying
the EU rules into `jurisdictions/france/rules/` with `jurisdiction_id: france`.
That would give a green demo and two divergent copies of the VAT Directive.

**Suggested fix.** A pack declares what it depends on, and the engine composes:

```yaml
# jurisdictions/france/jurisdiction.yaml
depends_on:
  - eu
```

`loadPack` resolves each dependency to a sibling pack root, loads its rules,
and `evaluate()` accepts a rule whose `jurisdiction_id` is the pack's **or any
declared dependency's**. `EvaluatedRule` should keep the origin visible so a
result can say *this came from the EU pack*; the UI needs that distinction and
so does a reader auditing an answer.

Precedence is the open design question and this lane has no standing to settle
it. The France pack has none of the conflicts that would force it: the EU rules
here answer *where* and *whether in scope*, France answers *what* and *how
much*, and `eu-t-nft-place-of-supply-still-answered` shows the two composing
without collision. But a national rule that contradicts a supranational one is
a real case in EU VAT, and returning both — as competing interpretations
already do under §100 — is more honest than picking a winner in the loader.

This needs `jurisdiction.schema.json` to accept `depends_on`, which is
Steward's. Note that `jurisdictions/france/jurisdiction.yaml` already carries
`parent_jurisdiction: eu`; that field is about geography, not about rule
composition, and overloading it would make "France is in the EU" mean "run EU
rules", which is not the same statement.

## 3. `rule.schema.json` has no way to reference another rule

Plan 15 §79 asks for `references: [eu:vat:...]` on a France VAT rule. The rule
schema is `additionalProperties: false` and offers `sources`, `supersedes`,
`superseded_by` and `interpretations` — none of which means *this rule builds
on that one*. `sources` is the nearest and is wrong: an EU rule is not a
source, and putting it there would make the `references` check demand a
`source_id` that does not exist.

**Suggested fix:** a `references: { type: array, items: slug }` field on
`rule.schema.json`, checked by `references.ts` against declared `rule_id`s the
same way `supersedes` already is. Small, and it makes the plan's own example
expressible.

## 4. `jurisdiction_facts` is boolean-only, which is limiting exactly here

`EvaluateInput.jurisdiction_facts` is `Record<string, boolean>`. The EU rules
delivered by P0-3-04 fit inside that — `customer_is_taxable_person`,
`supply_is_electronically_supplied_service` — but a place-of-supply answer is
naturally *a country*, and the pack can only classify — the effect is
`PLACE_OF_SUPPLY_WHERE_CUSTOMER_ESTABLISHED`, not a Member State.

This is **not** a request to widen the DSL: a small versioned predicate
language is a deliberate constraint (plan 05 §29) and the classification-only
result is defensible. It is a note that the first consumer to want "which
Member State" will find no way to express the input, and that whoever adds
string facts should do it in the DSL version, not by loosening the type.

## 5. Not blocking, but worth knowing

`packages/rules-engine` may not import `jurisdictions/` (`imports.ts` forbids
it) and nothing in CI loads a real pack, so items 1 and 2 could not have been
caught by the existing tests. A fixture pack with two jurisdictions, one
depending on the other, would catch both and would have caught the France
citation gap months earlier.

## What P0-3-04 shipped in the meantime

`jurisdictions/eu/` is a complete pack in its own right: seven sourced rules,
25 tests executed against `evaluate()` while authoring, an explicit
`unsupported.yaml`, and a `RESEARCH.md` that says what is not indexed. It is
referenced from the France VAT explanation by `source_id` and by link, which is
as far as plan 15 §79 can be honoured with today's engine.

None of the above changes what the EU pack says. It changes whether France can
run it.

## Resolution (Steward, 2026-09-09)

The two schema items (§2's schema half and §3) are applied on `main`. Items 1,
2's engine half, and 5 are changes under `packages/rules-engine`,
`packages/source-registry` and `tests/`, which are not Steward's paths — they
stay with the engines and QA lanes. §4 is explicitly not a request and is left
as the note it is.

**§3 — added, and checked.** `rule.schema.json` gains `references`: an array of
rule ids, unique, for the rules this rule builds on. `references.ts` now
validates it against declared `rule_id`s, and deliberately does **not** accept a
source id as a fallback the way `supersedes` does — putting an EU rule in
`sources` is the confusion the field exists to remove, so that case gets its own
message:

```
references points at source_id "…"; cite authorities in sources, not references
```

Three regression tests cover it: a France rule referencing an EU rule validates
clean, an unknown rule id fails, and a source id in `references` fails with the
message above.

**§2's schema half — added, with a caveat stated in the schema itself.**
`jurisdiction.schema.json` gains `depends_on`. Your point about
`parent_jurisdiction` is right and is now written into the field description, so
the next reader does not have to rediscover it: geography and rule composition
are different claims, and overloading the former would make "France is in the
EU" mean "run the EU pack's rules".

The description also says the field is **declarative only** — declaring a
dependency does not by itself make another pack's rules fire. That matters,
because the schema now accepts something the engine ignores. Landing it anyway
is deliberate: `additionalProperties: false` meant the data could not exist
before the schema allowed it, so this unblocks the engines lane and the France
lane to move independently rather than in sequence.

Verified on the real pack rather than in a fixture: adding `depends_on: [eu]` to
`jurisdictions/france/jurisdiction.yaml` and
`references: [eu-vat-place-of-supply-services-b2b]` to a France VAT rule
validates with 0 errors. Those probe edits were reverted — making them for real
is the France lane's call, and there is no hurry while §2's engine half is open.

**On §1, which is the one that worries me most.** Confirmed and unchanged: a
rule whose sources are *all* foreign resolves to an empty `sources` array with
no error, so AC-001 passes by accident. Two loaders with one truth — the
validator reading the whole tree while the engine reads one directory — is now
the root cause of three separate findings across RFC P0-3-03 and this one. The
fix belongs with the engines lane, but the divergence itself is worth treating
as a design defect rather than three bugs.

**On §5.** Agreed, and it is the same gap noted in the P0-3-03 resolution: a
two-jurisdiction fixture pack where one depends on the other would have caught
both §1 and §2. It cannot land before §1 and §2 do, and it should land with
them rather than after.
