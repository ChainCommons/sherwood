# RFC P0-3-03 — the France rules cannot run in CI, and two engine bugs are why

**Lane:** france · **TODO:** P0-3-03 · **Raised:** 2026-09-09
**Owners of the fix:** Engines (`packages/source-registry`, `packages/rules-engine`),
QA (`tests/`), Steward (`vitest.config.ts`, `schemas/`)

Filed per the shared preamble: everything below is outside
`jurisdictions/france` and `jurisdictions/eu`, so this lane did not touch it.
P0-3-03 ships green — `pnpm validate`, `pnpm typecheck` and `pnpm test` all
pass — but the pack's 52 rule tests do not run in CI, and two of the four items
below are the reason they cannot yet.

All four were found by writing the France rules, not by reading the code.

---

## 1. The engine's YAML parser cannot read any knowledge pack (blocker)

`packages/source-registry/src/yaml.ts` handles the block scalar indicators `|`
and `>`, but not the **chomping indicators** `>-`, `|-`, `>+`, `|+`. Every
France source, every explanation and every rule uses `>-`, because that is what
`title:` and `notes:` want: a folded scalar without a trailing newline.

The result is that `loadPack()` throws on the France pack:

```
SyntaxError: unexpected indent at line 8
    at parseMapping (packages/source-registry/src/yaml.ts:85:13)
    at readDataFile (packages/source-registry/src/load.ts:30:10)
    at loadSourcesFromDir (packages/source-registry/src/load.ts:134:17)
    at loadPack (packages/rules-engine/src/pack.ts:215:14)
```

`title: >-` is not matched by the `rest === '|' || rest === '>'` branch, so it
is stored as the literal string `">-"`, the parser advances one line, and the
next (indented) line is read as a sibling key.

Verified fix: with the patch below applied, `loadPack('jurisdictions/france')`
returns 13 rules, 2 interpretations and 32 sources, and `evaluate()` answers
correctly. The patch was tested and then reverted — `packages/` is not this
lane's to change.

**This is worse than it looks:** `pnpm validate` passes, because
`packages/validate` reads YAML with the real `yaml` library while the engine
hand-rolls its own. A green validator therefore does not mean the engine can
load the pack. Nothing in CI exercises `loadPack()` against a real jurisdiction
directory, which is how a whole pack came to be unreadable without a red build.

Reproduce:

```ts
import { parseYaml } from './packages/source-registry/src/yaml.ts'
parseYaml('title: >-\n  hello\nnext: 1\n')   // throws
parseYaml('title: >\n  hello\nnext: 1\n')    // { title: 'hello ', next: 1 }
```

**Suggested fix**, in `parseMapping` and `parseSequence` — accept the indicator
with an optional chomp, and strip a trailing newline for `-`:

```ts
const m = /^([|>])([-+]?)$/.exec(rest)
if (rest === '' || m) {
  if (m) {
    const block = parseLiteralBlock(lines, i + 1, indent + 1, m[1] === '|')
    obj[key] = m[2] === '-' ? String(block.value).replace(/\n+$/, '') : block.value
    i = block.next
  } else { /* unchanged */ }
}
```

The alternative — rewriting the 30-odd France source records to avoid `>-` —
was rejected. The YAML is valid; the parser is not, and `permitted_extract` in
particular holds text whose exact bytes matter.

**Better still**, take the dependency. `yaml@2.9.0` is already in the lockfile
for `packages/validate`, so adding it to `packages/source-registry` costs a
workspace edit rather than a new package, and deletes 200 lines of parser that
two lanes have now had to work around. That is Steward's call
(`pnpm-lock.yaml`), which is why it is a request and not a patch.

## 2. A rule citing another pack's source loses the citation silently (blocker)

Plan 15 is explicit: *"France VAT rules `references: [eu:vat:...]` rather than
copy-paste."* `fr-nft-vat-unsettled-before-2024` follows it — its only two
sources are `eu-dir-2006-112-vat` and `eu-cjeu-c-264-14-hedqvist`.

`loadPack('jurisdictions/france')` builds a registry from
`jurisdictions/france/sources` alone, and `SourceRegistry.resolveAsOf()` drops
unknown ids without complaint:

```ts
for (const id of sourceIds) {
  const s = this.byId.get(id)
  if (s) out.push(viewAsOf(s, d))   // an unknown id vanishes here
}
```

`attachSources()` then guards on `rule.sources.length`, which is 2, rather than
on the *resolved* length, which is 0. So the rule is emitted looking sourced
and carrying nothing:

```
fr-nft-vat-unsettled-before-2024 declared sources: 2 -> resolved: 0
```

That is an AC-001 violation reached through the front door, and it is exactly
the "appearance of authority" failure `references.ts` was written to prevent —
except `references.ts` validates against the whole repo and the engine loads
one directory.

**Suggested fix**, two parts:

- `loadPack` should resolve a pack's `parent_jurisdiction` (France declares
  `eu`) and load the parent's sources too, or take a registry the caller has
  already populated.
- `attachSources` should throw, or record a gap, when a declared source id does
  not resolve. Silence is the bug; whether it fails hard or degrades is a
  design call for the engines lane.

Until part one lands, any consumer of this pack must load
`jurisdictions/eu/sources` alongside `jurisdictions/france/sources`. The test
runner in §4 does this, and one test case
(`fr-t-nft-vat-cites-eu-sources-that-must-resolve`) asserts both citations
resolve, so the fix is already covered.

## 3. `interpretation.schema.json` cannot be used with its own `rule_id`

Same shape as §1 of [`P0-3-01.md`](P0-3-01.md), which is now the second
instance of this class.

`schemas/rule/interpretation.schema.json` offers `rule_id` as the foreign key
back to the rule an interpretation reads. Two checks treat any document with a
`rule_id` as a *rule*:

- `unique-ids.ts` counts the foreign key as a second declaration:
  `duplicate rule_id "fr-nft-disposal-perimeter-unsettled-2019-2025"`.
- `temporal.ts` demands `published_from`, which the interpretation schema does
  not define and `additionalProperties: false` forbids adding.

So an interpretation using the field fails CI two ways, and the field is
unusable. `references.ts` already models the right shape.

**Suggested fix**, in `unique-ids.ts`, extending the existing `declaresId`
carve-outs:

```ts
const declaresId = (field: string, doc: Record<string, unknown>): boolean => {
  if (field === 'jurisdiction_id') return typeof doc.jurisdiction_type === 'string'
  if (field === 'source_id') return doc.source_version_id === undefined
  if (field === 'rule_id') return doc.interpretation_id === undefined
  return true
}
```

and in `temporal.ts`, narrowing the rule test the same way:

```ts
const isRule = typeof d.rule_id === 'string' && d.interpretation_id === undefined
```

**Worked around in this PR:** the two France interpretations carry no
`rule_id`. The link runs the other way, from the rule's `interpretations: []`,
which `evaluate.ts` already resolves — so nothing is lost except the ability to
write the interpretation stand-alone.

## 4. The rule tests have nowhere to run

`vitest.config.ts` includes `packages/*/test/**/*.test.ts` and
`tests/**/*.test.ts`. Neither reaches `jurisdictions/`, and `plans/agents/lane-qa.md`
says QA owns `tests/` while "France/Events provide data". So this lane shipped
the data — 52 cases in `jurisdictions/france/tests/*.yaml`, format documented
in [`tests/README.md`](../../jurisdictions/france/tests/README.md) — and cannot
ship the runner.

Please adopt the runner below as `tests/jurisdiction/france-rules.test.ts`. It
needs no `vitest.config.ts` change — `tests/**/*.test.ts` is already included —
but it does need `yaml` as a root `devDependency`. Today `yaml@2.9.0` is in the
lockfile only as a dependency of `packages/validate`, so a test under `tests/`
cannot import it:

```
Error: Failed to load url yaml (resolved id: yaml) in tests/jurisdiction/france-rules.test.ts
```

That is Steward's to add (root `package.json`, `pnpm-lock.yaml`), and fixing §1
by taking the dependency in `packages/source-registry` would settle both.

**What the runner does today, measured rather than predicted.** All 52 cases
were executed against `evaluate()` while authoring, loading the pack with a
spec-compliant YAML parser and the EU sources registered — **52/52 pass**, so
the rules and the expectations agree.

Run instead through the real `loadPack()` with the §1 parser patch applied and
`yaml` resolvable, but **without** the §2 fix:

```
Test Files  1 failed (1)
     Tests  8 failed | 44 passed (52)
```

Every one of the eight failures is §2 and nothing else — they are the cases
touching `fr-nft-vat-unsettled-before-2024`, whose two EU citations resolve to
nothing, caught by the runner's AC-001 assertion:

```
AssertionError: expected [] to have a length of 2 but got +0
  ❯ expect(find(id).contemporaneousSources).toHaveLength(want)
```

So §1 and §2 are the whole distance between this data and a green CI run, and
`fr-t-nft-vat-cites-eu-sources-that-must-resolve` is the case that will tell
you when §2 is done.

```ts
import { readdirSync, readFileSync } from 'node:fs'
import { join } from 'node:path'
import { parse as parseYaml } from 'yaml'
import { describe, expect, it } from 'vitest'
import { evaluate, loadPack } from '../../packages/rules-engine/src/index.ts'

const PACK = join(process.cwd(), 'jurisdictions/france')
const TESTS = join(PACK, 'tests')
const pack = loadPack(PACK, { jurisdiction_id: 'france' })
const sorted = (xs: readonly string[]): string[] => [...xs].sort()

for (const file of readdirSync(TESTS).filter((f) => f.endsWith('.yaml')).sort()) {
  const suite = parseYaml(readFileSync(join(TESTS, file), 'utf8'))
  describe(suite.test_suite_id, () => {
    for (const c of suite.cases) {
      it(`${c.test_id} — ${c.matrix.join('/')}`, () => {
        const i = c.input
        const result = evaluate({
          pack,
          event: i.event ?? {},
          participant: i.participant ?? {},
          ...(i.jurisdiction_facts ? { jurisdiction_facts: i.jurisdiction_facts } : {}),
          asOf: { transactionDate: i.as_of.transaction_date, analysisDate: i.as_of.analysis_date }
        })
        const e = c.expect
        expect(result.status).toBe(e.status)
        expect(sorted(result.applicable.map((x) => x.rule.rule_id))).toEqual(sorted(e.applicable_rule_ids))
        expect(sorted(result.laterGuidance.map((x) => x.rule.rule_id))).toEqual(sorted(e.later_guidance_rule_ids ?? []))
        for (const id of e.not_applicable_rule_ids ?? []) {
          expect(result.applicable.map((x) => x.rule.rule_id)).not.toContain(id)
        }
        if (e.certainty_level) expect(result.certainty.level).toBe(e.certainty_level)

        const evaluated = [...result.applicable, ...result.laterGuidance]
        const find = (id: string) => {
          const er = evaluated.find((x) => x.rule.rule_id === id)
          expect(er, `rule ${id} was not evaluated`).toBeDefined()
          return er!
        }
        for (const [id, want] of Object.entries(e.effects ?? {})) {
          expect(find(id).rule.effects).toMatchObject(want as object)
        }
        for (const [id, want] of Object.entries(e.interpretations ?? {})) {
          expect(sorted(find(id).interpretations.map((x) => x.interpretation_id))).toEqual(sorted(want as string[]))
        }
        for (const [id, want] of Object.entries(e.published_after_transaction ?? {})) {
          expect(find(id).publishedAfterTransaction).toBe(want)
        }
        for (const [id, want] of Object.entries(e.contemporaneous_source_count ?? {})) {
          expect(find(id).contemporaneousSources).toHaveLength(want as number)
        }
        for (const frag of e.gaps_include ?? []) {
          expect(result.gaps.join(' ')).toContain(frag)
        }
        // AC-001: nothing is emitted without a resolved source.
        for (const er of evaluated) expect(er.sources.length).toBeGreaterThan(0)
      })
    }
  })
}
```

## 5. DSL v0 has no numeric jurisdiction fact

`DslContext.jurisdiction_facts` is `Record<string, boolean>`, so a threshold
that is *not* a property of the event cannot be expressed in a predicate. The
France case is the 305 € floor: it is measured on the taxpayer's **total
disposal proceeds for the calendar year**, so no single event carries it, and
`event.amount` — the one numeric field `readField` exposes — is the wrong
number. Using it would silently turn an annual test into a per-transaction one.

The pack therefore asks the caller for
`annual_disposal_proceeds_over_305_eur` as a boolean and does the comparison
outside the engine, which means the euro boundary lives in the test cases
(`fr-t-floor-exactly-305-eur-2021`, `fr-t-floor-305-eur-and-one-cent-2021`) and
not in any rule. That works, but it moves a piece of the rule out of the rule,
and the next jurisdiction with a banded rate or a holding-period threshold will
hit it harder than France does.

Widening the type to `Record<string, boolean | string>` would be enough —
`asComparableNumber` in `dsl.ts` already accepts decimal strings, and plan 17
§89 wants money as strings rather than floats anyway, so the comparison
operators would work unchanged. Not urgent for P0; recorded because the
workaround is invisible from the rule alone.

Two smaller asks that would make the data self-checking rather than
convention-checked:

- **A rule-test schema.** These files declare no `$schema` because none exists,
  so `pnpm validate` parses them and moves on — a typo in `expect` is caught
  only by the runner, and a typo in `covers` by nothing. A
  `schemas/scenario/rule-test.schema.json` (or similar) would close that.
- **A `covers` reference check.** `references.ts` could treat a test case's
  `covers[]` as a foreign key onto `rule_id`, the way it already does for
  `sources[]`. A test naming a rule that no longer exists should fail loudly,
  and today it does not fail at all.

## One design observation, not a bug

`evaluate()` derives the result's certainty from `applicable[0]` — the first
rule in load order, which is filename order. Where two rules legitimately apply
to one event (in France: the charge and the basis rule both fire on a disposal)
the overall certainty depends on how the files happen to be named. The France
tests assert `certainty_level` only where a single rule applies, so they do not
depend on it. Worth a look, but this lane has no view on what the right answer
is — a maximum, a minimum, or a set.

## Resolution (Steward, 2026-09-09)

Items 3 and the tooling half of items 1/4 are applied on `main`. Items 1 and 2
are engine changes under `packages/source-registry` and `packages/rules-engine`,
which are the rules lane's owned paths, not the Steward's — they are left open
for that lane, with the findings below confirmed independently.

**All four reproduce.** Verified before changing anything:

```
parseYaml('title: >-\n  hello\nnext: 1\n')  -> THROWS: unexpected indent at line 2
parseYaml('title: |-\n  hello\nnext: 1\n')  -> THROWS: unexpected indent at line 2
parseYaml('title: >\n  hello\nnext: 1\n')   -> { title: 'hello', next: 1 }
loadPack('jurisdictions/france')            -> FAILS: unexpected indent at line 8
```

So the report is exact: the engine cannot load the France pack, and `pnpm
validate` stays green while that is true. The blind spot is real and is the most
valuable thing in this RFC.

**Item 3 — fixed.** `unique-ids.ts` gains the `rule_id` carve-out and
`temporal.ts` narrows its rule test, both keyed on `interpretation_id`:

```ts
if (field === 'rule_id') return doc.interpretation_id === undefined
const isRule = typeof d.rule_id === 'string' && d.interpretation_id === undefined
```

Four regression tests in `packages/validate/test/checks.test.ts`: a rule with two
interpretations validates clean and needs no `published_from`, while two rules
sharing a `rule_id`, two interpretations sharing an `interpretation_id`, and a
genuine rule missing `published_from` all still fail. The France interpretations
can now carry `rule_id` directly; migrating them is the France lane's call, and
nothing breaks until it happens.

This is the third instance of the foreign-key-as-declaration class, after
`jurisdiction_id` and `source_id`. The carve-outs are now three special cases in
one predicate. If a fourth arrives, the right fix is to invert the rule — declare
per document *type* which field it declares — rather than add another line.

**Item 4 — Steward's half done.** `yaml@^2.9.0` is now a root `devDependency`
and recorded in the lockfile, so a test under `tests/` can import it. Verified
with a throwaway spec under `tests/jurisdiction/` that parsed `>-` correctly and
was then removed. Adopting the runner itself is QA's (`tests/` is theirs), and it
will stay red until item 1 lands — 8 of the 52 cases fail without item 2, exactly
as measured here.

**Item 1 — the dependency question, answered.** Taking `yaml` in
`packages/source-registry` is now a one-line edit for the engines lane:
`yaml@2.9.0` is already resolved in the lockfile, so adding
`"yaml": "^2.9.0"` to that package's dependencies and re-running install costs
no new resolution. Steward has no objection to the dependency and prefers it to
maintaining a hand-rolled parser that two lanes have now had to work around. The
choice between patching and replacing remains the engines lane's.

**The CI gap is not yet closed, deliberately.** Nothing exercises `loadPack()`
against a real jurisdiction directory, which is how this shipped green. The
obvious guard — a test that loads every `jurisdictions/*` pack — cannot land
until item 1 is fixed, because it would fail on `main` today. It should land in
the same change as item 1 rather than after it; a fix without the guard leaves
the same hole open for the next parser gap.
